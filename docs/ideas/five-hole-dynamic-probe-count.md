# 五孔探针数量动态化（Dynamic Probe Count）

## Problem Statement
How might we 让五孔移位测试模块从「固定 3 探针 + 启用/禁用」演化为「用户可按需增减探针数量（上限 6）」，一站式满足多测点五孔同步测量需求——而不重构现有共享布点网格与同步语义？

## Recommended Direction
**方向 A：极简动态化**——去除前端硬编码的 3 探针上限，复用现有 `v-for` 动态渲染与后端切片式 `Probes []FiveHoleProbeConfig`，在设置弹窗新增「添加/删除探针」交互，上限 6。超出 3 根时主界面横向滚动，保持现有大卡片体验不变。

后端零改动（切片本无上限、`motion_coordinator.go` 同步等待语义已天然支持 N 根）；前端工作集中在 store 去字面量化、设置弹窗增删 UI、布局溢出滚动三处。这是「修魔法数字」而非「架构升级」——刻意不做探针托管实体化、不引入 Probe Rake 概念、不做紧凑视图双轨制，把抽象留给真正需要时。

选择理由：用户已确认「共享布点网格、4-6 根、保持现有体验、真实项目驱动」，现有架构已就绪，最小改动即可解锁能力。若 4-6 根滚动大卡片实测拥挤，再升级为方向 C（紧凑视图）作为增量演进。

## Key Assumptions to Validate
- [ ] **「最慢探针」节奏假设**：6 根同步语义下每布点等最慢探针，若 1 根位移机构明显慢会拖垮整体节奏。测试：模拟设备构造「1 慢 5 快」跑 9 点矩形布点，记录每点耗时。
- [ ] **设备共享 batchGetter 竞态**：多探针共用一台采集设备时，`data_processor.go` 的「按设备分组并行 + 通道合并 batchGetter」在 6 根场景是否仍安全。测试：构造 6 探针全共用 1 台 16 通道设备的单测。
- [ ] **6 根位移机构硬件就绪**：6 根 × 2 轴 = 12 轴 = 3-6 台位移控制器。确认硬件台数，且 `MotionControllerManager` 10 Hz 轮询在 6 台时无性能退化。
- [ ] **横向滚动可读性**：4-6 根大卡片（每张 ~280px）在 1920 屏宽下横向滚动是否可接受。开发原型后实测，若拥挤则触发升级至方向 C。

## MVP Scope
**In:**
1. **前端 store**（`src/frontend/src/stores/fiveHoleTest.ts`）：
   - `PROBE_IDS` 常量改为 `generateProbeIds(n)` 函数
   - `probeLabels`（`FiveHoleTestView.vue:576`）改为计算属性 `probeLabel(probeId)` → `探针 N`
   - `calibLoadedMap` / `calibFilesMap`（`fiveHoleTest.ts:97-98`）去 `probe1/2/3` 字面量，改为空对象 + 动态读写
   - 新增 `addProbe()` / `removeProbe(probeId)` action，常量 `MAX_PROBES = 6`
2. **设置弹窗**（`FiveHoleTestView.vue` 设置 tab 探针配置区）：
   - 头部加「+ 添加探针」按钮（`config.probes.length < 6` 时可用）
   - 每根探针配置块加「删除」按钮（运行中禁用；至少保留 1 根）
3. **主界面探针卡片容器**：加 `overflow-x: auto`，超出 3 根横向滚动
4. **类型注释更新**：`five_hole_traversal.go:62` `// probe1/probe2/probe3` → `// probe1..probeN (N≤6)`；前端 types.ts 同步
5. **测试**：更新 `fiveHoleTest.test.ts` 中硬编码 `probe1/2/3` 的断言为参数化；新增 4-6 根探针的配置/启停/导出用例

## Not Doing (and Why)
- **探针托管实体化（方向 B）**——本次需求未要求跨测试复用探针配置，引入管理页/CRUD 弹窗是把「修魔法数字」包装成「架构升级」。若未来确有复用需求，再独立提案。
- **Probe Rake 探针排架抽象（变体 5）**——用户已选「共享布点网格、现有架构」，rake 概念是更深的概念重构，超出本次范围。留作未来领域演进方向。
- **紧凑视图双轨制（方向 C）**——1-3 大卡片 / 4-6 紧凑条形两套 UI。先验证横向滚动够不够用；若实测拥挤，作为增量演进单独引入，不在本次 MVP 中并行实现。
- **探针模板预设（变体 7）**——保存「6 探针配置」为模板跨测试加载。本次是单次项目需求，模板化是后续可叠加层。
- **不设硬上限（变体 4）**——用户明确 4-6 根，`MAX_PROBES = 6` 既是 UI 约束也是防误操作护栏。
- **探针随硬件自动浮现（变体 2）**——隐式行为不可预测，违背「最小惊讶」，显式增删按钮更可控。
- **后端架构改动**——切片无上限、`motion_coordinator` 同步语义已支持 N 根、CSV 按探针独立导出已就绪。刻意保持后端零改，避免引入回归风险。

## Open Questions
- 6 根位移控制器的硬件是否就绪？（需确认台数与型号）
- 若某根探针位移机构故障/断连，同步语义下整个测试需停止——是否需要「单探针故障隔离」机制？（本次不做，记录为已知限制）
- `completeProbeDataPoints` 在 6 探针时的内存占用：每点 ×6 探针，布点规模大时可能显著——本次假设布点规模与 3 探针时一致。
